# ServerMonitor

ServerMonitor — Telegram-бот для мониторинга Linux-сервера. Он периодически проверяет системные показатели, диски, Docker-контейнеры и HTTP-сервисы, отправляет уведомления о проблемах и восстановлении, а по командам показывает состояние сервера в Telegram.

## Возможности

- **CPU:** загрузка, температура процессора и load average.
- **Память:** использование оперативной памяти и swap.
- **Диски:** разделы, точки монтирования, свободное место и температура.
- **NVMe SMART:** предупреждения контроллера, доступный резерв, израсходованный ресурс и рост счётчиков ошибок.
- **Docker:** состояние контейнеров, health status, признаки завершения из-за нехватки памяти и код выхода.
- **HTTP-сервисы:** проверка заданных адресов, коды ответа, время запроса и время последней успешной проверки.
- **Интернет-проверка:** доступность выбранного внешнего HTTP-адреса с сервера.
- **Уведомления:** настраиваемые пороги, подтверждение длительных проблем, повторные сообщения по cooldown и сообщения о восстановлении.
- **Telegram-команды:** просмотр текущих системных показателей и последних результатов HTTP- и SMART-проверок; доступ ограничивается списком разрешённых пользователей.

Бот предназначен для наблюдения за сервером: он не перезапускает контейнеры и не выполняет команды управления сервером из Telegram. Настройки задаются в `.env` и `config.yaml`, для фоновой работы предусмотрен запуск через systemd.

## Установка

Проект проверен на Linux с Python **3.13.5**.

### Системные зависимости

Перед установкой должны быть доступны:

- Python 3.13 с поддержкой `pip` и `venv`;
- Git;
- `smartctl` — пакет `smartmontools`, используется для получения температуры дисков;
- `nvme` — пакет `nvme-cli`, используется для чтения NVMe SMART;
- `lsblk` — обычно входит в пакет `util-linux`;
- `sudo`.

Для мониторинга контейнеров необходим работающий Docker Engine.

Способ установки системных пакетов зависит от дистрибутива Linux. Права доступа к Docker и дисковым утилитам настраиваются отдельно.

### Скачивание проекта

```bash
git clone https://github.com/vihruta/Servermonitoring.git
cd Servermonitoring
```

### Создание виртуального окружения

Проверьте установленную версию Python:

```bash
python3.13 --version
```

Создайте и активируйте виртуальное окружение:

```bash
python3.13 -m venv .venv
source .venv/bin/activate
```

### Установка конфигурации

Настройки находятся в двух файлах рядом с `main.py`:

- `.env` — токен Telegram и идентификаторы пользователей;
- `config.yaml` — параметры мониторинга.

При первой установке создайте их из примеров:

```bash
cp .env.example .env
cp config.example.yaml config.yaml
```

### Установка Python-зависимостей

```bash
python -m pip install -r requirements.txt
```

Проверьте совместимость установленных зависимостей:

```bash
python -m pip check
```

При успешной проверке появится сообщение:

```text
No broken requirements found.
```

### Проверка установки

Запустите автоматические тесты:

```bash
python -m pytest -q
```

После установки перейдите к настройке `.env`, `config.yaml` и прав доступа.

## Конфигурация

### Telegram: `.env`

```dotenv
TOKEN=YOUR_BOT_TOKEN
ALLOWED_USER=111111111,222222222
ALERTS_CHAT_ID=111111111
```

| Переменная | Назначение |
|---|---|
| `TOKEN` | Токен бота, полученный через BotFather |
| `ALLOWED_USER` | Числовые Telegram ID пользователей, которым разрешены команды; несколько ID разделяются запятыми |
| `ALERTS_CHAT_ID` | ID чата, в который бот отправляет уведомления |

`ALLOWED_USER` содержит ID пользователей, а не их `@username`. `ALERTS_CHAT_ID` задаёт получателя уведомлений и не заменяет список разрешённых пользователей.

Для получения сообщений в личном чате пользователь должен сначала открыть диалог с ботом и нажать «Запустить».

Не публикуйте `.env`. В репозитории хранится только `.env.example` с вымышленными значениями.

### Мониторинг: `config.yaml`

Все интервалы, задержки и таймауты задаются в **секундах**, температуры — в **°C**, загрузка и заполнение — в **процентах**.

| Раздел | Назначение |
|---|---|
| `monitoring` | Интервал общих проверок CPU, RAM, дисков и Docker |
| `thresholds` | Пороги системных метрик |
| `timeouts` | Таймауты `smartctl`, `lsblk` и Docker API |
| `docker` | Имена контейнеров для уведомлений и их cooldown |
| `http_services` | HTTP-проверки приложений |
| `internet` | Проверка доступности выбранного интернет-адреса |
| `smart` | Интервал NVMe SMART и пороги предупреждений |
| `logger` | Уровень и формат логирования |

Пауза `interval` выполняется после завершения прохода проверок, поэтому время между началами проходов может быть больше указанного интервала.

### Пороги системных метрик

Пример:

```yaml
warning: 85
critical: 95
recovery: 75
warning_duration: 120
cooldown: 300
```

- `warning` — значение, начиная с которого определяется предупреждение.
- `critical` — значение, начиная с которого определяется критическое состояние.
- `recovery` — значение, ниже которого фиксируется восстановление.
- `warning_duration` — время подтверждения предупреждения; критическое состояние не ждёт эту задержку.
- `cooldown` — пауза перед повторным уведомлением о продолжающейся проблеме.

Порог восстановления ниже порога предупреждения помогает избежать постоянного переключения состояний около одной границы.

### HTTP-сервисы

```yaml
http_services:
  interval: 60
  failure_duration: 120
  cooldown: 600
  monitored:
    my_app:
      url: https://app.example.com
      timeout: 10
      expected_status: [200]
```

- `my_app` — имя сервиса в сообщениях.
- `url` — полный адрес проверки, включая `http://` или `https://`.
- `timeout` — таймаут запроса.
- `expected_status` — допустимые HTTP-коды ответа.
- `failure_duration` — минимальная длительность отказа перед уведомлением.
- `cooldown` — интервал повторных уведомлений о продолжающемся отказе.

Для каждого дополнительного сервиса добавьте запись в `monitored`. Если HTTP-сервисы не нужны, используйте `monitored: {}`.

Имя `Internet` зарезервировано текущей реализацией для интернет-проверки — не используйте его для приложения.

### Проверка интернет-адреса

```yaml
internet:
  url: https://example.com
  timeout: 10
  expected_status: [200]
  interval: 60
  failure_duration: 120
  cooldown: 600
```

Эта проверка показывает доступность выбранного адреса с сервера. Его недоступность сама по себе не доказывает отсутствие доступа ко всему интернету.

### NVMe SMART

```yaml
smart:
  interval: 3600
  timeout: 10
  cooldown: 600
  available_spare_warning: 10
  percentage_used_warning: 20
```

- `interval` — пауза между проходами SMART.
- `timeout` — таймаут отдельной внешней команды.
- `cooldown` — пауза повторных уведомлений о состоянии диска.
- `available_spare_warning` — предупреждение при резерве ниже этого процента.
- `percentage_used_warning` — предупреждение при израсходованном ресурсе, равном порогу или превышающем его.

NVMe-устройства обнаруживаются автоматически. Рост `media_errors` и `num_err_log_entries` обрабатывается отдельно как событие.

После изменения конфигурации перезапустите бота.

## Права доступа

Бот запускается от обычного пользователя Linux. Этот пользователь должен:

- читать файлы проекта, конфигурацию и виртуальное окружение;
- иметь доступ к Docker API;
- выполнять необходимые команды чтения дисков без запроса пароля.

Во всех примерах ниже `BOT_USER` нужно заменить именем существующего пользователя, от которого запускается бот. Для systemd это пользователь из поля `User=`.

### Доступ к `.env`

Если `.env` принадлежит пользователю бота, ограничьте доступ к файлу:

```bash
chmod 600 .env
```

Это разрешает чтение и запись только владельцу файла.

### Доступ к Docker

Для стандартного Docker Engine с группой `docker` добавьте пользователя бота в эту группу:

```bash
sudo usermod -aG docker BOT_USER
```

Членство в группе `docker` предоставляет возможности уровня root. Добавляйте в неё только доверенного пользователя.

Для применения изменения в интерактивной сессии выйдите из неё и войдите снова. Если бот уже работает через systemd, перезапустите его сервис.

Проверьте доступ из сессии пользователя бота:

```bash
docker ps
```

Команда должна работать без `sudo`.

### Чтение дисков через sudo

Узнайте пути установленных программ:

```bash
command -v nvme
command -v smartctl
```

Определите устройства:

```bash
lsblk -o NAME,PATH,TYPE,MOUNTPOINTS
sudo nvme list -o json
```

Создайте отдельный файл правил:

```bash
sudo visudo -f /etc/sudoers.d/servermonitor
```

Пример для одного NVMe-диска:

```sudoers
BOT_USER ALL=(root) NOPASSWD: /usr/sbin/nvme list -o json
BOT_USER ALL=(root) NOPASSWD: /usr/sbin/nvme smart-log /dev/nvme0n1 -o json
BOT_USER ALL=(root) NOPASSWD: /usr/sbin/smartctl -A -j /dev/nvme0n1
```

Замените:

- `BOT_USER` — имя пользователя Linux, от которого запускается программа;
- пути программ — результатами `command -v`;
- `/dev/nvme0n1` — реальным устройством.

Для каждого дополнительного диска добавьте отдельные необходимые правила. Например, для температуры SATA-диска:

```sudoers
BOT_USER ALL=(root) NOPASSWD: /usr/sbin/smartctl -A -j /dev/sda
```

Аргументы должны соответствовать командам, которые выполняет сборщик. Для `smartctl` указывается целый диск, например `/dev/sda`, а не раздел `/dev/sda1`.

Правила разрешают конкретные команды чтения. Разрешение `NOPASSWD: ALL` боту не требуется.

Проверьте синтаксис:

```bash
sudo visudo -c
```

Затем из сессии пользователя бота проверьте команды:

```bash
sudo -n /usr/sbin/nvme list -o json
sudo -n /usr/sbin/nvme smart-log /dev/nvme0n1 -o json
sudo -n /usr/sbin/smartctl -A -j /dev/nvme0n1
```

Используйте свои пути программ и устройств. Команды должны выполняться без запроса пароля и возвращать JSON.

Обнаружение NVMe автоматическое, но при добавлении нового диска для него потребуется добавить соответствующее правило доступа.


## Запуск

### Вручную

Из каталога проекта выполните:

```bash
.venv/bin/python main.py
```

Проверьте ответы бота на `/help`, `/status`, `/services` и `/disk`. Ошибки будут отображаться в терминале.

Для остановки нажмите `Ctrl+C`.

### Через systemd
Перед запуском сервиса остановите экземпляр бота, запущенный вручную.

Создайте рабочий файл сервиса из примера:

```bash
cp servermonitor.example.service servermonitor.service
```

Отредактируйте в нём:

- `User` — имя Linux-пользователя бота;
- `Group` — его основную группу;
- `WorkingDirectory` — абсолютный путь к каталогу проекта;
- `ExecStart` — абсолютные пути к Python виртуального окружения и `main.py`.

Например:

```ini
User=monitor
Group=monitor
WorkingDirectory=/home/monitor/Servermonitoring
ExecStart=/home/monitor/Servermonitoring/.venv/bin/python -u /home/monitor/Servermonitoring/main.py
```

Пользователь и группа должны существовать. Замените примеры своими значениями.

Установите сервис:

```bash
sudo cp servermonitor.service /etc/systemd/system/servermonitor.service
sudo systemctl daemon-reload
sudo systemctl enable --now servermonitor.service
```

### Управление сервисом

Проверить состояние:

```bash
systemctl status servermonitor.service
```

Посмотреть последние сообщения журнала:

```bash
journalctl -u servermonitor.service -n 100 --no-pager
```

Следить за журналом:

```bash
journalctl -u servermonitor.service -f
```

Если просмотр журнала недоступен текущему пользователю, выполните команду через `sudo`.

Перезапустить после изменения кода или конфигурации:

```bash
sudo systemctl restart servermonitor.service
```

Остановить:

```bash
sudo systemctl stop servermonitor.service
```

После изменения самого файла сервиса повторно скопируйте его в `/etc/systemd/system/`, выполните `daemon-reload` и перезапустите сервис.

## Команды Telegram

Команды доступны пользователям, перечисленным в `ALLOWED_USER`.

| Команда | Что показывает |
|---|---|
| `/status` | Общая сводка: CPU, память, диски, SMART, Docker, HTTP-сервисы и интернет-проверка |
| `/cpu` | Загрузка, температура процессора и load average |
| `/ram` | Использование оперативной памяти и swap |
| `/disk` | Разделы, свободное место, температура дисков и подробные данные SMART |
| `/temp` | Температуры процессора и дисков |
| `/docker` | Состояние Docker-контейнеров |
| `/services` | Последние HTTP-проверки сервисов и время последнего успеха |
| `/network` | Последний результат проверки интернет-адреса |
| `/help` | Список команд |

HTTP- и SMART-данные берутся из последних фоновых измерений. Вызов команды не запускает новую проверку этих показателей.

## Уведомления

Бот отправляет уведомления в чат `ALERTS_CHAT_ID`.

- `WARNING` — предупреждение о проблеме.
- `CRITICAL` — критическое состояние или событие.
- `RECOVERED` — восстановление после проблемы.

Для системных метрик задержка `warning_duration` помогает отсеивать кратковременные превышения порога предупреждения. Критические значения обрабатываются без этой задержки.

HTTP- и интернет-проверки используют `failure_duration`: уведомление отправляется, когда отказ подтверждён в течение заданного времени.

`cooldown` ограничивает повторные уведомления о продолжающейся проблеме. Новые события роста SMART-счётчиков обрабатываются отдельно.

Если во время сбоя интернет-проверки уведомление отправить не удалось, после восстановления бот пытается сообщить о завершившемся сбое.

## Ограничения

- Состояния, снимки измерений и таймеры хранятся в оперативной памяти и сбрасываются при перезапуске.
- Первое измерение SMART-счётчиков задаёт начальные значения. Само по себе ненулевое начальное значение не считается ростом.
- SMART-сборщик предназначен для NVMe-устройств.
- Проверка одного интернет-адреса отражает доступность этого адреса, а не всего интернета.
- Данные в командах могут быть получены раньше момента запроса. Для HTTP и SMART отображается время последней проверки.
- При недоступности Telegram доставка уведомлений может задерживаться. Постоянной очереди сообщений на диске нет.
- Сбор CPU-метрик сейчас рассчитан на датчик `k10temp`. Если этот датчик отсутствует, недоступен весь блок CPU: температура, загрузка и load average. Поддержка других датчиков пока не реализована.
